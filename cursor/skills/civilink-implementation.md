# CiviLink機能実装マッピング

## 機能設計原則

### ISO9001適合性を軸とした設計

```yaml
設計優先順位:
  P0: ISO9001適合必須機能
  P1: 日本市場必須機能（照査制度、電子納品等）
  P2: 差別化・付加価値機能
  P3: 将来拡張機能

アプローチ:
  - 規格要求をそのまま機能に落とし込まない
  - ユーザーワークフローに統合した形で実装
  - 「規格適合の証跡」が自然に残る設計
```

## P0：ISO9001適合必須機能

### 1. 版管理システム

#### ISO要求との対応

| ISO要求 | 条項 | 機能要件 |
|---------|------|----------|
| 変更の管理（例えば版の管理） | 7.5.3 c) | バージョン管理 |
| 適切な識別 | 7.5.3.2 a) | 版番号、改訂日の明示 |
| 保管・保存 | 7.5.3.2 b) | 全版の保存 |

#### 機能仕様

```yaml
バージョン採番:
  形式: Major.Minor.Patch（例：v2.1.3）
  自動採番: 保存時に自動インクリメント
  手動設定: 重要な節目でMajor更新可能

改訂履歴管理:
  必須項目:
    - 版番号
    - 改訂日時
    - 改訂者
    - 改訂内容（差分サマリー）
    - 改訂理由
    - 承認者（承認済みの場合）
  自動記録: 保存時に自動生成
  手動追記: 改訂理由は手動入力を推奨

最新版管理:
  表示: 最新版を視覚的に明示（バッジ、色分け）
  デフォルト: 常に最新版を表示
  警告: 旧版を開く際に警告表示

旧版管理:
  保存: 全ての旧版を保存
  識別: 「旧版」「アーカイブ」ラベル
  アクセス制限: 旧版の編集不可（読取専用）
  参照リンク: 旧版から最新版へのリンク
```

#### UI/UX設計指針

```yaml
版履歴表示:
  - サイドパネルまたはドロップダウンで版一覧
  - タイムライン形式での変更可視化
  - 版間比較機能への直接アクセス

版間比較:
  - 任意の2版を選択して比較
  - 差分ハイライト（追加:緑、削除:赤、変更:黄）
  - テキスト・図面両対応

ユーザーワークフロー:
  1. 文書を開く → 自動的に最新版
  2. 編集 → 自動保存でMinorバージョンアップ
  3. 正式版として確定 → 手動でMajorバージョンアップ
  4. 旧版参照 → 明示的な操作で切り替え
```

### 2. 承認ワークフローシステム

#### ISO要求との対応

| ISO要求 | 条項 | 機能要件 |
|---------|------|----------|
| 適切性及び妥当性についてのレビュー・承認 | 7.5.2 c) | 承認ワークフロー |
| 変更を正式に許可した人の記録 | 8.5.6 | 承認者記録 |

#### 機能仕様

```yaml
承認ルート設定:
  テンプレート:
    - 単純承認（担当→承認者）
    - 段階承認（担当→照査→管理）
    - 並列承認（複数承認者の同時承認）
  カスタマイズ: プロジェクト・文書種別毎に設定可能

承認アクション:
  - 承認
  - 差戻し（コメント必須）
  - 却下（理由必須）
  - 委任（代理承認者指定）

承認記録:
  必須項目:
    - 承認者名
    - 承認日時
    - 承認ステータス
    - コメント
  電子署名: タイムスタンプ付き電子署名
  改ざん防止: 承認記録の編集不可

通知機能:
  - 承認依頼通知
  - 承認完了通知
  - 差戻し通知
  - 期限超過リマインダー
```

#### 承認権限マトリクス設計

```yaml
文書種別 × 変更区分 × 承認者:

設計図面:
  軽微変更: 担当技術者
  通常変更: 照査技術者
  重要変更: 管理技術者
  重大変更: 技術審査会 + 発注者

設計計算書:
  軽微変更: 担当技術者
  通常変更: 照査技術者
  重要変更: 管理技術者

仕様書:
  全ての変更: 管理技術者以上
```

### 3. 変更管理システム（ECR/ECN）

#### ISO要求との対応

| ISO要求 | 条項 | 機能要件 |
|---------|------|----------|
| 変更のレビュー・管理 | 8.5.6 | ECR/ECNプロセス |
| レビュー結果の記録 | 8.5.6 | 影響評価記録 |
| 必要な処置の記録 | 8.5.6 | 対応処置記録 |

#### 機能仕様

```yaml
ECR（Engineering Change Request）:
  入力項目:
    - 変更対象文書
    - 変更内容（詳細記述）
    - 変更理由
    - 変更要因区分（発注者指示/現場条件/法令改正/VE提案/その他）
    - 要求者
    - 希望実施時期
  
  影響評価:
    - 技術的影響（構造、機能への影響）
    - 品質への影響
    - 工程への影響
    - コストへの影響
    - 安全への影響
    - 関連文書への影響（自動検出）

ECN（Engineering Change Notice）:
  生成条件: ECRが承認された場合
  内容:
    - 承認された変更内容
    - 実施方法
    - 実施時期
    - 影響を受ける文書一覧
    - 関係者一覧
  配信: 関係者への自動通知

変更実施追跡:
  - 変更対象文書の改訂ステータス
  - 実施完了チェック
  - 残作業アラート
```

#### 変更管理ダッシュボード

```yaml
表示項目:
  - 未処理ECR数
  - 承認待ちECR数
  - 実施中ECN数
  - 完了ECN数（期間別）

フィルタ:
  - プロジェクト
  - 文書種別
  - 変更要因
  - ステータス
  - 担当者

アラート:
  - 長期未処理ECR
  - 期限超過ECN
  - 関連文書未更新
```

### 4. トレーサビリティシステム

#### ISO要求との対応

| ISO要求 | 条項 | 機能要件 |
|---------|------|----------|
| 一意の識別を管理 | 8.5.2 | 文書識別コード |
| 文書化した情報として保持 | 8.5.2 | 追跡記録 |

#### 機能仕様

```yaml
文書識別コード:
  体系: [PRJ]-[種別]-[分野]-[連番]-[版]
  自動生成: 文書登録時に自動採番
  一意性保証: システム全体で重複なし

文書間リンク:
  リンク種別:
    - 参照（この文書がXを参照）
    - 被参照（この文書をXが参照）
    - 派生（この文書はXから派生）
    - 関連（この文書とXは関連）
  
  自動検出:
    - 文書内のID参照を自動検出
    - リンク候補の提示
  
  手動設定:
    - ドラッグ&ドロップでリンク作成
    - リンク種別の選択

依存関係グラフ:
  表示:
    - ノード: 文書
    - エッジ: リンク関係
    - 方向: 参照の方向
  
  機能:
    - ズーム/パン
    - ノード選択で詳細表示
    - 影響範囲のハイライト

変更影響分析:
  トリガー: 文書変更時
  分析内容:
    - 直接影響を受ける文書
    - 間接影響を受ける文書（2次以降）
    - 影響度スコア
  アクション:
    - 影響文書の担当者への通知
    - レビュー依頼の自動生成
```

| ISO要求 | 条項 | 機能要件 |
|---------|------|----------|
| 適切に保護 | 7.5.3.1 b) | アクセスログ |
| 機密性の喪失、不適切な使用、完全性の喪失からの保護 | 7.5.3.1 b) | 改ざん防止ログ |

#### 機能仕様

```yaml
記録対象操作:
  文書操作:
    - 作成
    - 閲覧
    - 編集
    - 削除
    - ダウンロード
    - 印刷
  
  ワークフロー操作:
    - 承認依頼
    - 承認/差戻し/却下
    - コメント追加

    - ログイン/ログアウト

    - 設定変更

  - タイムスタンプ（ミリ秒精度）
  - 操作者ID
  - 操作者名
  - 操作種別

  - 変更前値（該当する場合）
  - 変更後値（該当する場合）
  - IPアドレス
  - ユーザーエージェント

保護機能:
  - ログの追記のみ（削除・編集不可）
  - ハッシュチェーンによる改ざん検知
  - 定期的な整合性チェック

検索・分析:
  - フリーテキスト検索
  - フィルタ（期間、操作者、操作種別等）
  - レポート出力（監査用）
```

#### 対応要件

- 照査業務効率化

```yaml

  ベクタ比較:
    - 図形要素として比較
    - 意味のある差分を検出
    - 処理速度：中速

    - テキスト抽出後に比較

    - 比較対象ファイル情報
```

## API設計方針

### RESTful API原則

```yaml
命名規則:
  - リソース名は複数形
  - 小文字、ハイフン区切り
  - 動詞は使用しない（HTTPメソッドで表現）

エンドポイント例:
  GET    /api/v1/documents
  GET    /api/v1/documents/{id}
  POST   /api/v1/documents
  PUT    /api/v1/documents/{id}
  DELETE /api/v1/documents/{id}
  
  GET    /api/v1/documents/{id}/versions
  POST   /api/v1/documents/{id}/versions
  
  GET    /api/v1/change-requests
  POST   /api/v1/change-requests
  PUT    /api/v1/change-requests/{id}/approve
  PUT    /api/v1/change-requests/{id}/reject
```

### 認証・認可
